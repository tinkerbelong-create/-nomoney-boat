# アクアリウム設計書

3つの課題（賭博リスク / 未経験者の入口 / 同時接続の上限）を、
**「的中すると魚が増える水槽」** を軸に一度に解く設計。

- 作成: 2026-08-06
- 状態: 設計。実装前。
- 対象コミット: `docs/badges.md` および `supabase/migrations/0017_prize_pledge.sql` 時点

---

## 0. なぜ水槽が3つとも効くのか

いまポイントは **増えるだけで出口がない**。
出口がないものを人は「換金できるのでは」と想像する。
「これ何の意味があるの？」の次に来る質問は必ず「賞品でも出るの？」になる。

水槽は **一方通行の出口** をつくる。
的中 → 魚が増える → 水槽が育つ。魚は売れないし譲れないし戻せない。
出口が可視化された瞬間、「勝ったポイントの行き先は魚」という答えが用意され、
換金性の想像が入り込む隙間がなくなる。

同時に、ボートレースを知らない人に **収支ランキング以外の目的** を与える。
そして水槽は静的なUIなので、負荷対策の余地も大きい（後述）。

| 課題 | 水槽がどう効くか |
|---|---|
| ① 賭博に見える | ポイントの行き先が「魚という記録」だと画面上で自明になる。景品が主役から降りる |
| ② 未経験者の入口がない | 「当たると魚が増える」は競技知識ゼロで理解できる。艇番カラー＝魚の色で自然に枠番を覚える |
| ③ 同時接続の上限が不明 | （水槽自体は解決しない。§5 で別途対策。ただし水槽は完全に静的なのでキャッシュが効く） |

## 1. 基本ルール

### 1.1 魚はポイントで買わない

**これが設計の要。**

魚は「的中した」という出来事に対して自動で付与される。
ポイントを消費しない。つまり **ポイントと魚のあいだに交換レートが存在しない**。

交換レートがあると、魚に「◯◯pt相当」という値段が付く。
値段が付いたものは価値を持ち、価値を持つものは換金の対象になりうる。
だから最初からレートを作らない。

魚は既存の **称号（バッジ）とまったく同じ性質のもの** になる。
「実績の記録」であって「所有物」ではない。
バッジがすでに問題なく成立しているのだから、魚も同じ土俵に乗せるのが一番安全で、
実装も既存の `award_badges` の構造をそのまま流用できる。

### 1.2 逆流路をひとつも作らない

以下は **実装しない**。将来も実装しない。

- 魚 → ポイントへの売却
- 魚のユーザー間譲渡・交換・トレード
- 魚のプレゼント機能
- 魚の売買市場

DB関数は `award_fish()` の1本だけを用意し、
`delete` / `transfer` / `sell` にあたる関数を **そもそも定義しない**。
RLS も `user_fish` に対して `select` のみを許可し、
`insert` / `update` / `delete` は `authenticated` に一切与えない（`security definer` 関数経由のみ）。

「作らない」ではなく「作れない」状態にしておく。

### 1.3 いまのポイント制度との関係

現行のポイント制度（`0014_points.sql`）は以下。

- 入会時に 50,000pt（1人1回だけ）
- **毎週木曜に 5,000pt**
- **リセットなし。** 残高は `point_ledger` 全体の合計

> **2026-08-06 修正済み。** 以前は README・DEPLOY.md・オンボーディング画面・
> 招待メッセージが「毎月1日に50,000pt・月末リセット」のままだった。
> とくに `onboarding/page.tsx` と `ShareInvite.tsx` は
> **新規ユーザーと招待相手が最初に読む文章** だったので、影響が大きかった。

リセットがないということは、**ポイントは永久に増え続ける**。
勝っている人の残高は青天井になり、5,000pt/週の支給も止まらない。
出口がないままだと、半年後には「残高10万pt。で？」になる。

**つまり水槽（＝出口）の必要性は、当初想定より高い。**
リセットで強制的に帳消しになる仕組みがない以上、
積み上がったものに意味を与える先を用意しないと、数字がただのノイズになる。

魚も永続だが、これは問題ない。ポイントと違って **上限のあるコレクション** だからだ
（艇番魚だけが無限に増えるが、それは「買い方の記録」なので増えて構わない）。

## 2. 魚の獲得トリガー

すべて **精算時（`settleEvent` 内）** に判定する。
既存の `award_badges(p_user_id)` を呼んでいる真横に `award_fish(p_user_id, p_event_id)` を追加する。

```
apps/web/src/core/settle.ts:115 付近
  await supabase.rpc('award_badges', { p_user_id: id });
+ await supabase.rpc('award_fish',   { p_user_id: id, p_event_id: eventId });
```

判定は何度呼んでも同じ結果になる（`on conflict do nothing`）。
バッジと同じく、バッチの再実行に対して安全。

### 2.1 艇番魚 — 毎回もらえる基本の魚

**的中した買い目の「頭」の艇番** に対応する魚が1匹増える。
ボートレースの艇番カラーをそのまま魚の色にする。

| 艇番 | 色 | 魚 | 由来 |
|---|---|---|---|
| 1号艇 | 白 | シロメダカ | 白い小魚。イン逃げの象徴として最初に手に入る |
| 2号艇 | 黒 | クロメダカ | 黒。差しの位置 |
| 3号艇 | 赤 | アカヒレ | 赤い熱帯魚。まくりの位置 |
| 4号艇 | 青 | ルリスズメダイ | 鮮やかな青の海水魚 |
| 5号艇 | 黄 | キイロハギ | 黄一色のヤッコ |
| 6号艇 | 緑 | ミドリフグ | 緑の汽水フグ。6号艇の的中は貴重なのでフグ |

教える必要がない。遊んでいれば覚える。

匹数は上限を設けず、同じ魚が何匹でも増える。
水槽を見れば **その人の買い方の癖** が一目でわかる（白ばかりの水槽 ＝ 1号艇信者）。
既存の `lane1_30`「1号艇信者」バッジと同じ発想を、視覚に置き換えたもの。

### 2.3 レア魚の抽選 — ★1〜★10 と排出率グリッド

**ここがこの企画の心臓部。**

的中したとき、**払戻倍率と掛け金の2軸** でグレード（1〜10）が決まり、
グレードごとに違う確率で **★1〜★10 の魚** が1匹出る。

#### 軸1：払戻倍率（7段階）

既存の `odds_10` 〜 `odds_1000` バッジと閾値を揃える。

`10倍未満 / 10〜30 / 30〜100 / 100〜300 / 300〜500 / 500〜1000 / 1000倍以上`

#### 軸2：掛け金（5段階・1000ptで頭打ち）

このアプリは **100pt刻みでしか賭けられない**（実際の舟券と同じ）。
なので刻みに合わせた段階にする。

`100pt / 200〜400pt / 500〜700pt / 800〜900pt / 1000pt〜`

**1000pt で完全に頭打ち。これが重要。**
青天井にすると「10万pt賭ければ確実に★10」になり、
ポイントを積むほど報酬が確定する仕組み＝ガチャに近づく。
上限を切れば **それ以上賭けても一切得しない** ので、無茶なベットを誘わない。

登録50,000pt・毎週5,000ptという経済のなかで、**1000pt は誰でも払える額**。
「金を積める人が有利」にならない水準に、意図的に低く置いている。

#### 35マスのグレード表

グレードは合成式ではなく **表として直接持つ**。
式にすると「10倍未満に大金を賭けたら★10が出る」のような、
意図しない組み合わせが生まれてしまうため。

| 倍率 \ 掛け金 | 100pt | 200〜400 | 500〜700 | 800〜900 | 1000pt〜 |
|---|---|---|---|---|---|
| **1000倍以上** | G8 | G8 | G9 | G9 | **G10** |
| 500〜1000倍 | G7 | G7 | G8 | G8 | G9 |
| 300〜500倍 | G6 | G6 | G7 | G7 | G8 |
| 100〜300倍 | G5 | G5 | G6 | G6 | G6 |
| 30〜100倍 | G3 | G4 | G4 | G5 | G5 |
| 10〜30倍 | G2 | G2 | G3 | G3 | G4 |
| **10倍未満** | **G1** | G1 | G1 | G2 | G2 |

そして G1〜G5 は★10の確率が 0%。**構造として★10が出ない。**

**100〜300倍の行は最大でも G6（★10が3%）で止めてある。**
万舟を当てても、掛け金を上げてシーラカンスの確率を伸ばすことはできない。

#### 検証した10項目（`docs/scripts/fish_rates.py` で自動チェック）

「矛盾がない」を、機械が判定できる条件に落として全部通してある。

| # | 条件 | 意味 |
|---|---|---|
| 1 | 各行の合計がちょうど100 | 丸め誤差で99や101にならない |
| 2 | 負の値がない | |
| 3 | **確率的単調性（FOSD）** | どの★閾値で見ても、Gが上がれば「その★以上」の確率が下がらない |
| 4 | 期待値が厳密に単調増加 | ★1.46 → 2.20 → … → 10.00 |
| 5 | G1〜G5 の★10がすべて0 | |
| 6 | G6の★10が3、G10の★10が100 | |
| 7 | 100倍未満の全マスで★10が0 | グリッド側から見ても成立 |
| 8 | グリッドが右へ・上へ単調 | 賭け金を増やして、倍率が上がって、グレードが下がることがない |
| 9 | **単峰性** | ピークまで非減少・ピーク後は非増加。山がふたつにならない |
| 10 | **穴がない** | 「★9は出ないのに★10は出る」が起きない |

> 条件3が一番大事。これが崩れると「グレードが上がったのに★7以上を引く確率が下がった」
> という、遊んでいて気づかれる種類の矛盾になる。
>
> 条件10は実際に1回引っかかった。初版の G6 は ★9=0 なのに ★10=3 で、
> 「★9より★10のほうが出やすい」歪んだ形になっていた。★9=5 を明示して修正した。

**下3行が丸ごとゼロ。ここが「シーラカンスの壁」。**

#### この表が持っている性質（設計の意図）

1. **1000倍以上 × 1000pt → ★10 が確定（100%）。** 千倍は別格として扱う。
   35マスのうち、確定するのはこの1マスだけ
2. **100倍未満では★10が絶対に出ない。** いくら賭けても0%
3. **100倍帯は上限が3%。** 万舟を当てても、掛け金を上げて
   シーラカンスの確率を伸ばすことはできない
4. **10倍未満 × 100pt → 期待値 ★1.46。** 一番しょぼい的中は一番しょぼい魚
5. **腕だけでも十分報われる。** 1000倍を最低額の100ptで当ててもG8
   （★10が15%、★9が26%、期待値★8.34）
6. **1000pt以上は全部同じ。** 賭け金の吊り上げに意味がない

2・3・6が、この設計を「ガチャ」から遠ざけている部分。
**射幸性を上げているのは倍率であって、掛け金ではない。**
掛け金は「本気で買ったかどうか」を判定するだけの、上限つきの補正にすぎない。

**「ツ」がいちばん気に入っている。** 日本一短い市名なので、名前も一文字。
図鑑で1体だけ異様に短い枠があるのは、それ自体が話のネタになる。

#### 主をどう出すか

**所持しているかどうかは見ない。★10を引いたら、通常の4種＋その場の主 の5種から等確率で1つ。**
重複しても構わない。シーラカンスが2匹いてもいいし、
キンランキリュウが3匹いてもいい。**水槽なのだから同じ魚が何匹いてもおかしくない。**

```
★10 を引いた
 └ 候補 = 通常の★10（4種）＋ その場の主（1種）= 5種
    └ 等確率で1つ。重複可
```

つまり **★10を引いたとき、20%でその場の主**。
所持判定を入れないぶん実装も単純になり、
「持っているかどうかで確率が変わる」という説明しづらさもなくなる。

#### どこで出るか — 出現条件の割り当て

**300種を全部どこでも出すと、場を移動する理由がなくなる。**
そこで一部に条件をつける。ただし **枠の数を先に決めない。**

> **初版の失敗。** 最初は「地区ごとに10種」と枠を決めてから埋めた。
> その結果、ホタテガイ（北海道・青森）を中国地区に、
> キビナゴ（鹿児島）を近畿地区に入れるような、**事実に反する割り当てが多数まぎれた。**
> 数を揃えるために「本当は違うけどここに入れておこう」をやると、こうなる。
>
> **いまは根拠が言えるものだけに条件をつけ、言えないものは全部ベースに戻してある。**
> 監査の全記録は [`CONDITION-AUDIT.md`](./CONDITION-AUDIT.md)。

| 枠 | 種数 | 根拠の強さ |
|---|---|---|
| **ベース** | **170** | — どこでも出る |
| 水質限定 | 62 | **強い。** 生態で決まる（メダカは淡水、マサバは海水） |
| 地区限定 | 23 | **強い。** その土地の名物として実在するものだけ |
| 等級限定 | 33 | **なし。** ご褒美の設計。生態のふりはしない |
| 夜限定 | 12 | **なし。** ナイターの演出 |
| **計** | **300** | |

**種類数が地区ごとにバラバラなのは、そういうものだから。**
関東7・東海3・近畿3・四国3・中国3・九州4。
関東が多いのは「江戸前」という文化が実在して、名前のついた魚が多いから。
**偏りに理由があるなら、揃えないほうが正しい。**

**条件は1種につき1つだけ。組み合わせない。**
AND条件（「近畿の淡水のG1の夜だけ」）にすると理屈が追えなくなるし、
候補が枯れて抽選が止まる。

#### 抽選の手順

```
① 倍率 × 掛け金 → グレード → ★が決まる（§2.3 の表）
② その★の中から「このレースで出うる種」だけに絞る
      ベース ＋ その場の水質 ＋ その場の地区 ＋ そのグレード ＋ その時間帯
③ 残った候補から等確率で1種。重複可
```

**この形の良いところは、SG限定種が「SGでだけ候補に入る」ことで自然にレアになる点。**
確率をいじらなくても、SG開催が年間1〜2%しかないという事実がそのままレア度になる。

#### 4つの軸

**① 水質（淡水9 / 汽水5 / 海水10）** — 公式の分類そのまま

| 水質 | 場 |
|---|---|
| 淡水 | 桐生・戸田・多摩川・三国・びわこ・住之江・尼崎・芦屋・唐津 |
| 汽水 | 江戸川・浜名湖・蒲郡・津・福岡 |
| 海水 | 平和島・常滑・鳴門・丸亀・児島・宮島・徳山・下関・若松・大村 |

淡水にはメダカ・コイ・アユ・ヤマメ、汽水にはハゼ・ボラ・シジミ、
海水にはサバ・サザエ・サンゴ。**生態として正しい**ので、遊んでいるうちに
「戸田は淡水なんだ」と覚える。しかも水質は実際のレース予想に効く要素
（淡水は浮力が小さく体重差が出る）なので、**学習が予想の役に立つ。**

**② 地区（6地区）** — `packages/core/src/venues.ts` の `area` をそのまま使う

関東5場・東海4場・近畿4場・四国2場・中国4場・九州5場。
ご当地の魚を割り当てる。九州にケンサキイカ、中国にキジハタ、東海にサクラエビ。

**③ 等級（SG / G1 / G2 / G3 / 一般）— 限定種ではなく★の出やすさを動かす**

初版は「G2でしか出ない魚」を置いていたが、**やめた。**
「キンメダイがG2でしか出ない」理由は自然界になく、説明できない。
これは §2.3 の穴埋め問題とまったく同じ性質の嘘だった。

**代わりに、等級はグレードを底上げする。** 出る顔ぶれは変わらず、★が上がりやすくなる。

| 等級 | ボーナス |
|---|---|
| 一般 | +0 |
| G3 | +1 |
| G2 | +2 |
| G1 | +3 |
| SG | +4 |

**同じ的中でも、等級が高いほど良い★が出る**（掛け金100ptのとき）

| 倍率 | 一般 | G3 | G2 | G1 | SG |
|---|---|---|---|---|---|
| 1000倍以上 | ★8.34 | ★9.23 | ★9.23 | ★9.23 | ★9.23 |
| 500〜1000 | ★7.26 | ★8.34 | ★9.23 | ★9.23 | ★9.23 |
| 300〜500 | ★6.31 | ★7.26 | ★8.34 | ★8.34 | ★8.34 |
| 100〜300 | ★5.00 | ★6.31 | ★6.31 | ★6.31 | ★6.31 |
| 30〜100 | ★3.05 | ★4.00 | ★5.00 | ★5.00 | ★5.00 |
| 10〜30 | ★2.20 | ★3.05 | ★4.00 | ★5.00 | ★5.00 |
| 10倍未満 | ★1.46 | ★2.20 | ★3.05 | ★4.00 | ★5.00 |

**等級ボーナスは、当たりが小さいときほど効く。**
1000倍を当てたらもともと上限近くなので、等級を上げても頭打ちになる。
これは意図した挙動で、「大穴を当てたのに等級で差をつけられる」不快感を避けている。
逆に10倍未満のしょぼい的中は、一般で★1.46、SGで★5.00 と大きく変わる。
**SGに参加する価値が、いちばん報われにくい層に届く。**

**★10（シーラカンス）の確率は等級で1ミリも動かない。**

| 倍率 | 一般 | G3 | G2 | G1 | SG |
|---|---|---|---|---|---|
| 1000倍以上 × 1000pt | 100% | 100% | 100% | 100% | 100% |
| 500〜1000 | 40% | 40% | 40% | 40% | 40% |
| 300〜500 | 15% | 15% | 15% | 15% | 15% |
| 100〜300 | 3% | 3% | 3% | 3% | 3% |
| 30〜100 以下 | 0% | 0% | 0% | 0% | 0% |

倍率帯ごとに上限（`GRADE_CAP`）を置いてあるので、**等級では★10のルールを破れない。**
100倍未満は等級をいくら上げても★10が0%のまま。
G10（★10確定）に届くのは 1000倍 × 1000pt のマスだけで、これも等級では買えない。

**`events.grade` が既にある。** `apps/ingest/src/adapters/boatrace.ts` の
`detectGradeFromTitle()` が開催タイトルから判定して `events.grade` に入れている。
**新しくデータを取りに行く必要がない。**


**④ 夜だけ（12種）** — `deadline_at` が 16:30 以降

初版は 朝 / 昼 / 夜 の3枠にしていたが、**朝と昼は根拠がなかったのでやめた。**
「イワシは朝しかいない」も「海藻は昼だけ」も嘘なので、数合わせにしかならない。

**夜だけは演出としての根拠がある。** ナイターの水面と深海生物。

```
ミズクラゲ・オオカミウオ・ミズダコ・ヒョウモンダコ・オオグソクムシ
エチゼンクラゲ・カツオノエボシ・ミズウオ
ラブカ・チョウチンアンコウ・デメニギス・フクロウナギ
```

**これも生態の根拠はない**（深海は昼も暗い）。演出だと割り切る。

場ごとのナイター表は持たない。**締切時刻だけで判定する。**
開催時間帯は年によって変わるので、固定表を持つと必ず古くなる。

> **未検証：夜のレースがない場では、この12種は永久に出ない。**
> これは仕様として受け入れる（プレイヤーはどの場にも賭けられるので詰みはしない）が、
> **「どの場に夜のレースがあるか」は実データを見るまで断定できない。**
> ★9のうち4種が夜限定なので、影響は小さくない。
> [`data/verify-before-implementing.sql`](./data/verify-before-implementing.sql) の
> ③を流して、場ごとの締切時刻の分布を必ず確認すること。

#### 検証（`docs/scripts/fish_conditions.py`）

**実在する場×時間帯の組み合わせだけ**を検証する。
夜のレースがない場で夜を検証しても意味がないので、
`VENUE_TIME` を見て、ナイター7場だけ夜のケースを回す。

```
検証: 全項目パス
候補数の最小値（実在する全組み合わせ中の最悪ケース）
  ★1:32  ★2:27  ★3:36  ★4:33  ★5:28
  ★6:19  ★7:18  ★8:13  ★9:5  ★10:4（＋場の主で5）
```

初版で薄かった★4は 5 → 33候補に改善した。
等級限定をやめてベースに戻したのと、穴埋めをやめた副産物。
**いま一番薄いのは★9の5候補**（昼のレース）。夜なら9候補。

開催時間帯マスタが24場ちょうどをカバーしているか（重複・欠落なし）も検査している。

**データの置き場所**

| ファイル | 用途 |
|---|---|
| `docs/scripts/fish_species.py` | 300種の正本。名前を変えるならここを直す |
| `docs/scripts/fish_conditions.py` | 出現条件の割り当てと360通りの検証 |
| `docs/scripts/venue_lords.py` | 24場の主の正本 |
| `docs/data/fish_species.csv` | 自動生成。一覧を眺めるとき用 |
| `docs/data/fish_species.sql` | 自動生成。`fish` テーブルへの seed |
| `docs/data/venue_lords.sql` | 自動生成。`fish` テーブルへの seed（`venue_code` 付き） |

`venue_lords.py` は **300種リストとの名前の衝突** も自動でチェックする。
`fish` テーブルに `venue_code` 列（null 可）を足し、
**null なら通常種・値が入っていれば場限定** と区別する。

```bash
python3 docs/scripts/fish_species.py --csv --sql
```

実行すると4項目を検証する。**重複した名前がない / 合計がちょうど300 /
★が上がるほど種類数が減っている / カテゴリが定義済みのもの**。
名前を足したり入れ替えたりしたら、必ず走らせて「全項目パス」を確認する。

**カテゴリの使いみち**

`魚 / 甲殻 / 貝 / 頭足 / クラゲ / 棘皮 / 海藻 / サンゴ / 海獣 / その他` の10種類。
図鑑のグループ分けだけでなく、**水槽のどこに描くか** の判定に使う。

| カテゴリ | 水槽での位置 | 動き |
|---|---|---|
| 魚・頭足・海獣 | 中層 | 左右に泳ぐ |
| クラゲ | 上層 | ゆっくり漂う |
| 甲殻・棘皮・貝 | 底 | 底を這う／止まる |
| 海藻・サンゴ | 底に固定 | 揺れるだけ |

これで **300種ぶんの絵を1枚ずつ描かなくても、水槽が成立する。**
カテゴリごとの動きのパターンと、種類ごとのシルエット＋色の組み合わせで作る。

#### 実装メモ

- **グレード表も排出率も、コードではなくテーブルの行として持つ。**
  賭け式やバッジと同じ方針。調整が `UPDATE` 1行で済む
- **乱数はDB側（`award_fish` の中）で引く。** クライアントに引かせると
  リロードで引き直せてしまう
- **`user_fish` に `on conflict do nothing` が効かない。** 抽選結果は毎回違うので、
  「このレースの抽選はもう済んだか」を別に記録する必要がある。
  `fish_draws (user_id, event_id)` に一意制約を張り、
  **既に行があれば抽選しない**（バッチ再実行に対する安全性を保つ）
- **1回の的中で出る魚は1匹だけ。** 艇番魚（§2.1）・場の魚（§2.2）は
  これとは別に確定でもらえるので、万舟を当てれば結局3匹入る

## 3. 水槽の見た目と成長

### 3.1 水槽のランク

**ポイントを使わない。通算的中レース数で自動的に大きくなる。**
経済設計が不要になり、バランス調整の手間もゼロになる。

| ランク | 条件 | 見た目 |
|---|---|---|
| 金魚鉢 | 初期 | 小さい丸い鉢 |
| 小型水槽 | 通算5的中 | 横長の水槽 |
| 中型水槽 | 通算25的中 | 水草が生える |
| 大型水槽 | 通算100的中 | 背景に岩組み |
| 大水槽 | 通算300的中 | トンネル水槽 |
| 水族館 | 通算1000的中 | 建物になる |

既存の `hit_5` 〜 `hit_500` バッジと同じ指標なので、判定ロジックを流用できる。

### 3.2 装飾

バッジの取得と連動させる。**新しい判定を書かず、既存のバッジをそのまま条件にする。**

| 装飾 | 条件バッジ |
|---|---|
| 24場の旗 | `venue_all`（全国制覇） |
| 虹色のサンゴ | `bt_all`（六刀流） |
| 沈没船 | `lose_50`（50連敗）— 負けた記念も飾れるようにする |
| 王冠 | `title_*_champion`（月間王者） |
| 灯台 | `days_100`（皆勤100日） |

負けの記念を飾れるのは大事。**負けている人が水槽を見る理由になる。**
既存のバッジ体系がすでに「不名誉」を面白く扱っているので、その路線を継ぐ。

### 3.3 画面

- **`/aquarium`** — 自分の水槽。魚が泳ぐ。タップすると「いつ・どのレースで手に入れたか」
- **`/u/[handle]`** — フレンドのプロフィールに水槽を埋め込む。見に行ける
- **`/aquarium/book`** — 図鑑。未取得の魚はシルエット表示。**これが継続の主動力**
- タイムラインに「◯◯さんがリュウグウノツカイを釣り上げた」を流す

魚の描画は **SVG ＋ CSS アニメーション** で行う。
canvas / WebGL は使わない。理由は §5.4。

## 4. 大会機能は撤去する

**方針を変えた。文言を直して残すのではなく、機能ごと消す。**

### 4.1 実装は法的には白だった

先に読んだ結論を記録として残しておく。
`join_tournament()` / `advance_tournaments()` を追ったかぎり、

- 参加費は `point_ledger` から引かれ、同額が `tournament_ledger` に入る（**自分の中での財布の移動**）
- 終了時、残った大会ポイントは **その人自身に** 戻る
- **プールも再分配も存在しない。** 他人の参加費が優勝者に流れる経路がコード上にない
- 景品は主催者の自腹で、サイトは表示のみ。誓約と同意記録まで残していた

刑法185条の賭博は「偶然の勝敗により **財産上の利益** の得喪を争う」こと。
財産上の利益が動いていない以上、構成要件を欠く。**実装に問題はなかった。**

### 4.2 それでも撤去する理由

**炎上は法解釈で起きない。見た目で起きる。**

コードを読まない人にとって、画面に

> 参加費 5,000pt ・ 🎁 優勝 焼肉おごり

と並んでいたら、それは賭博の絵面になる。
`prizes.ts` のNGワード検知も誓約フローも、**スクリーンショットには写らない。**

文言を変えて残す案（「参加費」→「スタート持ち点」など）も検討したが、
**残すかぎり景品の自由入力欄が残り、そこが最大の火種**である事実は変わらない。

そして **水槽がその役割を引き受けられる。**
大会は「フレンドと競う枠組み」として作られたが、
場の主・水質・地区・等級で集める対象が増えたいま、
**競う理由は水槽が供給できる。** リスクだけが残る機能を抱える必要がない。

| クエリ | `lib/queries.ts` の `getMyTournaments` / `getTournament` / `getTournamentPledge` / `getTournamentRanking` / `getTournamentRaces` / `getTournamentsForEvent` |
| タブ | `components/TabBar.tsx` の大会タブ |
| 投票 | `place_bet` の `p_tournament_id` 引数、`BetPanel` の大会選択 |
| ワーカー | `advance_tournaments()` の呼び出し |
| 文書 | README の大会の説明、DEPLOY.md |

**DBのテーブルはすぐには落とさない。**
`tournaments` / `tournament_entries` / `tournament_races` / `tournament_ledger` と
`bets.tournament_id` は残したまま、**画面とAPIだけを外す**。

理由は2つ。
既に大会ポイントを使った投票の履歴があると、テーブルを落とすと収支が壊れる。
そして「やっぱり戻したい」となったときに、データが残っていれば戻せる。

落とすのは、稼働データが無いことを確認してから別のマイグレーションで行う。

### 4.4 撤去で軽くなること

- 景品の自由入力欄が消える → **炎上の火種がゼロになる**
- 誓約・同意記録・NGワード辞書の保守が不要になる
- `place_bet` の引数が減り、投票まわりが単純になる
- 大会ポイントという第二の財布が消え、**残高の計算が1本になる**（§5.3-⑤ の負荷対策が楽になる）
- 画面が1つ減る → SSRの本数が減る

## 5. 同時接続の上限と対策

### 5.0 前提：無料で運営し続ける

**有料プランに上げる選択肢は取らない。** 自腹を切らずに人数を伸ばす。

これは制約であると同時に、設計の指針になる。
「金で殴れない」なら、**バイトとCPUを構造的に減らすしかない**。

無料枠と、超えたときに何が起きるかを先に並べる。

| リソース | 無料枠 | 超えたら |
|---|---|---|
| **Supabase egress（非キャッシュ）** | **5GB/月** | 制限がかかる |
| Supabase egress（キャッシュ） | 5GB/月 | 同上 |
| **Vercel Fast Data Transfer** | **100GB/月** | **プロジェクトが停止（30日待ち）** |
| **Vercel Active CPU** | **4時間/月** | **同上** |
| Vercel Provisioned Memory | 360GB時間/月 | 同上 |
| Vercel 関数呼び出し | 100万/月 | 同上 |
| GitHub Actions（**publicリポジトリ**） | **無制限** | — |

**Vercel Hobby は超過分を買えない。** 枠を超えるとサイトが止まり、
30日経つまで戻らない。**課金される心配はないが、落ちる心配はある。**
だから §5.6 のセーフティバルブが要る。

**GitHub Actions だけが唯一「無制限」。** 重い処理はできるだけこちらに寄せるのが、
無料運営の基本方針になる（リポジトリを public にしておくこと）。

> **Supabase の自動一時停止（1週間無活動）は対策済み。**
> `daily.yml` が毎日DBを叩くので条件を満たさない。ただし
> **Actions を止めると1週間でプロジェクトが眠る** ので、そこだけ注意。

### 5.1 結論 —「同時◯人」ではなく「月◯ユーザー時間」

無料枠で先に尽きるのは **同時接続数ではなく月間の総量**。
なので上限は「ユーザー時間／月」（1人が1時間使う＝1ユーザー時間）で答える。

**現状のまま:**

| 制約 | 上限 |
|---|---|
| **Supabase egress 5GB/月** | **約900ユーザー時間/月** ← 最初に尽きる |
| Vercel Active CPU 4時間/月 | 約1,600ユーザー時間/月 |
| Vercel Fast Data Transfer 100GB/月 | 約18,000ユーザー時間/月 |
| Supabase Nano の共有CPU | 同時100人前後で遅延（瞬間風速） |

→ 毎日1時間使うヘビーユーザーなら **約30人** が限界。

**§5.3 の対策後（無料のまま）:**

| 制約 | 上限 |
|---|---|
| Supabase egress | 約11,000ユーザー時間/月 |
| **Vercel Active CPU** | **約5,000ユーザー時間/月** ← ここが新しい壁 |
| Vercel Fast Data Transfer | 約18,000ユーザー時間/月 |

→ 毎日1時間のヘビーユーザーで **300〜500人**、
週末だけのライトユーザーなら **2,000人以上**。**無料のまま。**

### 5.1.1 無料運営の核心：バイトの出どころを Supabase から Vercel に移す

Supabase の枠（5GB）と Vercel の転送枠（100GB）には **20倍の差** がある。
なのに現状は `force-dynamic` により、**すべてのバイトが Supabase から出ている**。

100人が同じレース一覧を見ると、Supabase から同じデータが100回出る。
これが「人数に比例して無料枠が溶ける」原因。

**データを2つに分けると、話が変わる。**

| | 中身 | 全体に占めるバイト |
|---|---|---|
| **共有データ**（全員同じ） | レース一覧・出走表・オッズ・結果・場マスタ・お題 | **約99%** |
| 個人データ（自分だけ） | 自分の投票・残高・フレンド・お気に入り・魚 | 約1% |

**バイトのほぼ全部が「全員に同じもの」なのに、人数分だけ Supabase から取り直している。**

共有データを Vercel のキャッシュに載せれば、
**何人見ても Supabase から出るのは1回分**になる。
ユーザーへの配信は Vercel の 100GB 枠を使うが、そちらは20倍の余裕がある。

これが **Supabase egress を人数から切り離す** ということで、
900 → 11,000 ユーザー時間の 12倍はここから来る。

### 5.2 数字の根拠

**レース詳細を1人が開いていると、1分あたりこれだけ発生する。**

`races/[eventId]/page.tsx` は `AutoRefresh intervalMs={20_000}` なので **3回/分の SSR**。
1回の SSR で走る Supabase へのリクエストを数えると:

| 呼び出し | 回数 |
|---|---|
| `middleware` の `supabase.auth.getUser()` | 1 |
| `requireProfile()`（getUser ＋ profiles） | 2 |
| `getBalance()` → `current_balances` | 1 |
| `getEvent()` | 1 |
| `getMyBetsForEvent()` | 1 |
| `getMarketResults()` | 1 |
| `getFavoriteRacers()` | 1 |
| `getFeatureForEvent()` | 1 |
| `getTournamentsForEvent()` | 1〜2 |
| **合計** | **約10** |

→ **1人あたり 約30リクエスト/分（0.5 req/s）を Supabase に投げている。**

**① Supabase egress（先に尽きる）**

無料枠は月10GB（キャッシュ5GB＋非キャッシュ5GB）。
DBのレスポンスは非キャッシュ側を食う。

```
1ユーザー時間 = 180 SSR × 10クエリ × 平均3KB ≒ 5.4 MB
5,000 MB ÷ 5.4 MB ≒ 925 ユーザー時間/月
```

出走表やオッズ（3連単は120通り）が乗ると1レスポンスが数十KBになるので、
実際はもっと早く尽きる可能性がある。

**② Vercel Hobby の Active CPU（2番目）**

Hobby は **Active CPU 4時間/月 ＋ Provisioned Memory 360 GB時間/月**。
Fluid Compute では、I/O待ちの時間は Active CPU に計上されない。
Next.js の SSR（Reactレンダリング＋JSONパース）で1回あたり 50ms 前後と見積もると:

```
4時間 = 14,400 CPU秒 ÷ 0.05秒 ≒ 288,000 SSR/月
288,000 ÷ 180 SSR/時 ≒ 1,600 ユーザー時間/月
```

Provisioned Memory 360 GB時間のほうは、Fluid が1インスタンスで複数リクエストを
捌くので、この規模ではまず尽きない。

**③ `api/odds` の特殊事情**

`maxDuration = 60`、`FETCH_TIMEOUT_MS = 25_000`。
外部fetchの待ち時間は Active CPU には乗らないが、
**Provisioned Memory には wall-clock で乗る**。
boatrace.jp が重い日に25秒待つ関数が並ぶと、360 GB時間のほうが先に減る。
§5.3-① ② で呼び出し回数自体を減らすのが正解。

**④ Supabase Nano の共有CPU（瞬間風速）**

無料プランは Nano インスタンス（共有CPU・小メモリ）。
単純な主キー引きなら数百 req/s 出るが、
**`current_balances` と `user_season_totals` が集計ビュー** なのが効いてくる（§5.3-⑤）。
同時100人（＝50 req/s）あたりから p95 が伸び始めると見ておく。

### 5.3 対策（効果の大きい順）

#### ⓪-A 共有データをキャッシュして、Supabase から人数分取らない ← 効果が最大

**Supabase egress を12倍に伸ばす、いちばん効く一手。**

いまはほぼ全ページが `export const dynamic = 'force-dynamic'`。
「全員に同じもの」まで人数分 Supabase から取り直している。

**共有データを `unstable_cache` でくるみ、タグで無効化する。**

```ts
// 例：レース一覧。全員同じなので1回取れば全員に配れる
export const getRacesForDate = unstable_cache(
  async (dateYmd: string) => { /* 既存の実装そのまま */ },
  ['races-for-date'],
  { revalidate: 60, tags: ['races'] },
);
```

| データ | キャッシュ期間 | 無効化のきっかけ |
|---|---|---|
| レース一覧・締切時刻 | 60秒 | ingest が締切処理をしたとき |
| 出走表 | 6時間 | `entrants` ジョブ実行後 |
| オッズ | 90秒（既存のDBキャッシュを流用） | — |
| レース結果・払戻 | **確定後は無期限** | 精算時に1回だけ |
| 場マスタ・賭け式・バッジ定義・魚定義 | 無期限 | マイグレーション時のみ |
| お題レース | 10分 | `feature` ジョブ実行後 |

**確定後の結果を無期限にできるのが大きい。** もう変わらないデータを
毎回DBに聞きにいく必要はない。過去レースの閲覧が実質タダになる。

無効化は ingest ワーカーから Webhook で叩く。

```
POST /api/revalidate?tag=races&secret=...
→ revalidateTag('races')
```

`daily.yml` / `ingest.yml` の最後に `curl` を1行足すだけ。
**GitHub Actions は public リポジトリなら無制限なので、ここは遠慮しなくていい。**

**個人データ（投票・残高・フレンド・魚）はキャッシュしない。**
全部合わせても数KBなので、キャッシュしなくても枠を圧迫しない。
むしろ古い残高が見えるほうが害が大きい。

#### ⓪-B AutoRefresh をページ全体のSSRから、軽量JSONに変える ← Vercel CPU に効く

⓪-A で Supabase 側が解決すると、**次の壁は Vercel の Active CPU 4時間/月** になる。

いまの `router.refresh()` は **ページ全体を再レンダリング** する。
1回あたり Active CPU 50ms 前後。3回/分 × 人数ぶん積み上がる。

しかし20秒ごとに実際に変わりうるのは、せいぜいこれだけ。

- 締め切ったか
- 結果が出たか
- 自分の残高が変わったか

**これを返すだけの Route Handler を作り、変化があったときだけ `router.refresh()` を呼ぶ。**

```ts
// GET /api/tick/[eventId] → { status, settled, balance }  200バイト程度
```

- Active CPU: 50ms → **5ms 程度**（10倍）
- 転送量: RSCペイロード約30KB → **200バイト**（150倍）

**変化がないときは何も再描画しない** ので、体感も軽くなる。
`AutoRefresh` を「ポーリングして差分があったら refresh する」に作り替える。

#### ① `BetPanel` の自動ポーリングが 90秒キャッシュを毎回破っている ✅ 修正済み（2026-08-06）

`BetPanel.tsx:121`

```js
const id = setInterval(() => run(true), 120_000);   // ← force = true
```

`force=true` は `?fresh=1` を付ける。
`api/odds` の実装では、`fresh=1` が来ると **締切前のレースについては
90秒キャッシュを飛ばして boatrace.jp に取りに行く**
（締切後は `closed` 判定で守られているので、そこは問題ない）。

問題は締切前。**オッズを一番見たい時間帯に、一番人が集まっているレースで、
一番外部アクセスが増える** という最悪の形になっている。

同じレースを50人が見ていたら、2分ごとに boatrace.jp へ50本のリクエストが飛ぶ。
Vercel のサーバーレスなので送信元IPもバラバラで、レート制限もかからない。

`apps/ingest/src/http.ts` では同時1本・1.2秒間隔・サーキットブレーカまで用意して
公式サイトに配慮しているのに、**Web側だけがそれを完全に迂回している。**
これは負荷の問題であると同時に、サイトポリシー（大量アクセスの禁止）に抵触するリスクでもある。

**修正:**

```js
const id = setInterval(() => run(false), 120_000);  // キャッシュに乗せる
```

これだけで外部アクセスが人数分の1になる。
`fresh=1` は手動の「更新」ボタンだけに限定する。

#### ② `api/odds` に単一飛行（single-flight）を入れる

①を直しても、キャッシュが切れた瞬間に同時アクセスが来ると
複数リクエストが同時に boatrace.jp を叩く（thundering herd）。

Postgres の advisory lock で「このレース × この賭け式を取りに行くのは1本だけ」にする。

```sql
-- 取得を試みる前に
select pg_try_advisory_xact_lock(hashtext(event_id || bet_type_code));
-- false なら fetch せず、あるキャッシュを返す（stale: true で返してよい）
```

ロックが取れなかったリクエストは待たずに古いキャッシュを返す。
オッズは目安なので、90秒古くても「何も出ない」よりずっとよい
（既存の `catch` 節がすでに同じ判断をしている）。

#### ③ `fresh=1` にユーザー単位のレート制限をかける

「更新」ボタン連打で外部アクセスが増えないよう、
`market_odds.fetched_at` を見て **30秒以内の再取得は無視** する。
UIのボタンも30秒間 disabled にする。

#### ④ `middleware` の `getUser()` を条件付きにする

`middleware.ts` は **すべてのリクエスト** で `supabase.auth.getUser()` を呼ぶ。
これは Supabase Auth へのネットワーク往復。AutoRefresh の RSC リクエストも全部通る。

Cookie に入っている JWT の `exp` を読み、**残り5分以上あればスキップ** する。
リフレッシュが必要なときだけ叩く。**リクエスト数がざっと半分になる。**

#### ⑤ `current_balances` / `user_season_totals` を集計テーブルにする

`point_ledger` に増減だけを記録して残高を `sum(amount)` で出す設計は
「残高が合わない」を構造的に防ぐ良い設計で、**これは変えるべきではない**。

ただし読み取りが O(行数) になる。**しかも `0014_points.sql` でリセットを廃止したので、
`current_balances` はシーズンで区切らず台帳全体を合計している。**

```sql
create view current_balances with (security_invoker = on) as
select l.user_id, coalesce(sum(l.amount), 0)::bigint as balance
from point_ledger l group by l.user_id;
```

インデックスは `point_ledger (user_id, season_code)` があるので
1人分のスキャンで済むが、**その1人分の行数が永久に増え続ける**。

1人が1日100点買えば月3,000行。1年で36,000行。
残高は Header に常時出るので **ほぼ全ページで毎回この合計を計算している**。
半年後に「なんとなく重い」が始まり、原因が分かりにくい類の劣化になる。

`user_season_totals`（ランキング）も同じ構造で、こちらは全ユーザー分を舐める。

**台帳はそのまま残し、集計だけをテーブルに持つ。**

```sql
create table balance_cache (
  user_id    uuid primary key references profiles(id) on delete cascade,
  balance    bigint not null default 0,
  updated_at timestamptz not null default now()
);

-- point_ledger の after insert トリガで加減算するだけ
create or replace function bump_balance_cache() returns trigger ... $$
  insert into balance_cache (user_id, balance) values (new.user_id, new.amount)
  on conflict (user_id) do update
    set balance = balance_cache.balance + excluded.balance, updated_at = now();
$$;
```

台帳が真実で、キャッシュは導出。ズレたら台帳から再計算すればよい。
**突き合わせを検算する関数を1本必ず用意する**（`sum(point_ledger)` と
`balance_cache.balance` が一致するかを全員分チェックして、
ズレた人だけ返す）。`daily.yml` から毎日叩いて、ズレたら警告を出す。

検算が用意できないキャッシュは入れないほうがいい。
このプロジェクトは「残高が合わない」を構造で防ぐことを設計の柱にしているので、
そこを崩さない形でだけ高速化する。

#### ⑥ `AutoRefresh` を締切までの残り時間で可変にする

いま一律 20秒。締切まで1時間あるレースを20秒ごとに更新する意味はない。

| 締切までの残り | 間隔 |
|---|---|
| 5分未満 | 15秒 |
| 5〜30分 | 45秒 |
| 30分以上 | 120秒 |
| 締切後・確定前 | 60秒 |
| 確定後 | 停止 |

**確定後に止めるのが効く。** いまは結果が出たあともずっと回り続けている。
平均で **リクエストが1/3以下** になる。

#### ⑦ 水槽ページは静的に寄せる

`/aquarium` は魚の一覧を出すだけで、リアルタイム性が要らない。
`revalidate = 300` にして、魚が増えたときだけ `revalidatePath()` で飛ばす。
**新機能を作るときに最初から負荷をかけない形にしておく。**

#### ⑧ Vercel Hobby の商用利用不可に注意

Hobby プランは非商用限定。このサイトは非営利のファンサイトなので現状は問題ないが、
広告を貼ったり投げ銭を受けたりした瞬間に規約違反になる。
**収益化しないことは、法的リスク管理の意味でも Vercel 規約の意味でも守ったほうがいい。**

無料運営を続けるなら、これは **守りやすい制約** でもある。
収益がないぶん、規約の面でも賭博の面でも立場がはっきりする。

#### ⑨ 重い処理は GitHub Actions に寄せる

**public リポジトリの GitHub Actions は完全無料・無制限。**
Vercel の Active CPU 4時間/月 と比べると、事実上いくらでも使える。

Vercel でやらなくていいものは全部こちらへ移す。

| 処理 | いま | 移したあと |
|---|---|---|
| 集計・ランキングの事前計算 | 毎回SSRで計算 | Actions で計算してテーブルに書く |
| 魚の付与判定 | 精算時（すでにActions側） | そのまま |
| 月間タイトル | Actions | そのまま |
| 画像・OGPの生成 | （未実装） | Actions で静的生成 |

**ランキングを事前計算するのが一番効く。**
`user_season_totals` をSSRのたびに集計せず、
`ingest.yml`（15分ごと）で計算済みテーブルに書いておく。
ホーム画面はそれを1行読むだけになる。

### 5.6 セーフティバルブ（落とさないための仕掛け）

**Vercel Hobby は枠を超えるとプロジェクトが止まり、30日間戻らない。**
課金される心配はないが、**ある日突然サイトが真っ白になる** のが怖い。

無料で運営するなら、**止まる前に自分から性能を落とす** 仕組みが要る。

**① 使用量カウンタを持つ**

```sql
create table usage_daily (
  day date primary key,
  ssr_count bigint default 0,      -- SSR / Route Handler の呼び出し回数
  odds_fetch_count bigint default 0, -- boatrace.jp への外部アクセス
  bytes_out bigint default 0        -- Supabase から出たおおよそのバイト数
);
```

正確でなくていい。**傾向が分かればいい。**

**② 月の残り日数と使用量から、自動で段階的に劣化させる**

| 消費ペース | 挙動 |
|---|---|
| 〜70% | 通常 |
| 70〜85% | AutoRefresh の間隔を2倍に。オッズの手動更新を60秒に1回へ |
| 85〜95% | AutoRefresh 停止（手動リロードのみ）。画面に案内を出す |
| 95%〜 | 新規登録を一時停止。既存ユーザーは閲覧・投票のみ可 |

**落ちるより、遅くなるほうがずっとマシ。**
「今月は混んでいるので更新を遅くしています」と出ていれば、
利用者は納得するし、こちらも慌てずに済む。

**③ 週1で自分に通知する**

`daily.yml` に「日曜だけ使用量サマリを出す」ステップを足す。
GitHub Actions のログに出すだけでも、異常なペースに気づける。

**④ 人数の上限を決めておく**

技術で伸ばせるのは §5.1 のところまで。それを超えたら、
**招待コード制にして新規登録を絞る** のが最も確実な手段になる。

すでに大会の招待コード（`invite_code`）の仕組みがあるので、
同じ考え方を登録に適用できる。上限に達しても、
「いまは満員です」と表示して待ってもらえばいい。**止まるよりいい。**

### 5.7 それでも足りなくなったら（無料のまま）

有料に上げずに、さらに伸ばす道はある。順に検討する余地があるという程度のメモ。

- **Cloudflare Workers / Pages に移す** — 無料枠が Vercel より大幅に緩く、
  R2 は egress 無料。ただし Next.js の App Router との相性を確認する必要がある
- **確定済みデータを GitHub リポジトリに置いて配る** — 過去レースの結果は
  もう変わらないので、Actions で JSON に書き出して push すれば、
  Supabase も Vercel も通らずに配れる
- **Supabase プロジェクトを分ける** — 無料は2プロジェクトまでなので、
  読み取り専用の複製を置いて負荷を分散する（運用は複雑になる）

いまは考えなくていい。**§5.3 をやり切れば当分は足りる。**

### 5.4 水槽を作るときに守ること

- **描画は SVG ＋ CSS アニメーション。** canvas / WebGL は使わない。
  requestAnimationFrame を回すとモバイルのバッテリーを食い、
  タブを開きっぱなしにされたときに CPU を占有する。
  CSS アニメーションならブラウザが裏タブで自動的に止める。
- **魚の数に上限表示を設ける。** 500匹の水槽を全部DOMに出すと固まる。
  同種は重ねて「×32」と数字で出し、泳がせるのは種類ごとに1〜3匹まで。
- **魚のデータは1回のクエリで取る。** `user_fish` を種類ごとに引かない。
  `group by fish_code` で集計済みの1行1種類にして返す関数を作る。

### 5.5 上限を実測する方法

見積もりは見積もりでしかない。公開前に一度測る。

1. **k6 でシナリオを組む** — ログイン → レース一覧 → レース詳細を20秒ごとに5分間、を N 並列
2. **N = 10 / 30 / 100 / 300 で回し、p95レイテンシが2秒を超える点を探す**
3. **Supabase ダッシュボード → Reports → Database** で
   - CPU 使用率
   - 最も遅いクエリ（ほぼ確実に `current_balances` が上位に来る）
4. **Vercel ダッシュボード → Usage** で GB-Hours の消費レートを見る
5. **boatrace.jp への外部リクエスト数** を `api/odds` にカウンタを入れて数える。
   **これが秒間1本を超えていないことを必ず確認する**（ingest 側の自主基準と揃える）

測ったら数字をこの文書に追記する。

## 6. DB設計

バッジ（`badges` / `user_badges`）とまったく同じ形にする。
**魚の定義はコードではなくテーブルの行として持つ。** 増やすのがタダになる。

```sql
-- =====================================================================
-- 0018_aquarium.sql
-- =====================================================================

create table if not exists fish (
  code        text primary key,
  name        text not null,
  description text not null default '',
  -- lane / venue / payout / bettype / tournament / special
  category    text not null,
  rarity      text not null default 'bronze'
                check (rarity in ('bronze','silver','gold','crown')),
  -- 描画用。SVGのidと基本色
  sprite      text not null,
  color       text not null default '#888888',
  -- 同じ魚を複数匹持てるか。艇番魚は true、場・配当・賭け式は false
  stackable   boolean not null default false,
  sort_order  int not null default 0
);

create table if not exists user_fish (
  user_id   uuid not null references profiles(id) on delete cascade,
  fish_code text not null references fish(code) on delete cascade,
  count     int  not null default 1,
  first_at  timestamptz not null default now(),
  last_at   timestamptz not null default now(),
  -- 初取得時のレース・大会など。タップしたときに出す
  meta      jsonb not null default '{}',
  primary key (user_id, fish_code)
);

create index if not exists user_fish_user_idx on user_fish (user_id, last_at desc);

alter table fish      enable row level security;
alter table user_fish enable row level security;

create policy fish_read on fish
  for select using (auth.uid() is not null);

-- 自分と承認済みフレンドの水槽だけ見える（user_badges と同じ条件）
create policy user_fish_read on user_fish for select using (
  user_id = auth.uid()
  or exists (
    select 1 from friendships f
    where f.status = 'accepted'
      and ((f.requester_id = auth.uid() and f.addressee_id = user_fish.user_id)
        or (f.addressee_id = auth.uid() and f.requester_id = user_fish.user_id))
  )
);

-- insert / update / delete は誰にも与えない。付与は security definer 関数のみ。
```

**`stackable` の意味**

- 艇番魚（6種）は `stackable = true`。的中のたびに `count` が増える
- 場・配当・賭け式・大会の魚は `stackable = false`。1匹だけ

`count` は「その艇番で何回当てたか」の記録そのもの。
水槽を見れば買い方の癖がわかるのはこれによる。

**付与関数**

```sql
create or replace function award_fish(p_user_id uuid, p_event_id uuid)
returns int
language plpgsql security definer set search_path = public as $$
  -- 対象レースの当たった投票だけを見て、該当する魚を積む
  -- on conflict (user_id, fish_code) do update set
  --   count = user_fish.count + case when f.stackable then excluded.count else 0 end,
  --   last_at = now()
$$;

revoke all on function award_fish(uuid, uuid) from public;
grant execute on function award_fish(uuid, uuid) to service_role;
```

**`service_role` にしか実行権を与えない。**
`authenticated` に渡すと、クライアントから任意に呼べてしまう。
バッジの `award_badges` と同じ扱い。

**画面用の読み取り関数**

```sql
-- 図鑑用。未取得も含めて全部返す（user_badge_list と同じ形）
create or replace function user_fish_list(p_user_id uuid)
returns table (code text, name text, description text, category text,
               rarity text, sprite text, color text,
               count int, first_at timestamptz, meta jsonb)
```

1回のクエリで水槽全体が取れる。§5.4 の「種類ごとに引かない」を守るため。

## 9. やらないと決めたこと

将来の自分と、コードを引き継ぐ人に向けて明記しておく。

- **魚をポイントで買えるようにしない。** 交換レートが生まれた瞬間に魚が値段を持つ
- **魚をポイントに戻せるようにしない**
- **魚をユーザー間で譲渡・交換できるようにしない**
- **魚のガチャを作らない。** ポイントを消費するガチャは、上の3つに触れなくても
  「ポイントを払って偶然で結果が決まる」構図になり、いまより悪くなる
- **参加者から集めた参加費を優勝者に渡す形にしない**（大会機能ごと撤去した）
- **広告・投げ銭・課金を入れない。** 非営利であることが、いくつかのリスクの前提になっている

| その他 | 5 | 1 | 6 | 這う |

### 11.2 動きは4種類しかない

**324体ぶんのアニメーションを作らない。** 動きはカテゴリで決まる4種類だけ。

| 型 | 体数 | 位置 | 動き |
|---|---|---|---|
| **泳ぐ** | 208 | 中層 | 左右に横断しながら上下に揺れる。向きは進行方向 |
| **這う** | 79 | 底 | 砂の上を左右にゆっくり往復 |
| **揺れる** | 26 | 底に固定 | 根元を軸に左右へ傾く |
| **漂う** | 11 | 上層 | ゆっくり斜めに移動しながら傘が伸縮する |

**1体につき用意するのは、SVGの絵とサイズと色だけ。** 動きは型から自動で決まる。
これで324体を現実的な工数に収められる。

### 11.2.5 水槽1つに30体まで

**1水槽の定員は30体。** 324体を全部飾るには **11水槽** 必要になる。

これは3つの意味を持つ。

1. **描画負荷の上限が決まる。** 30体なら CSS アニメーションで軽々動く。
   324体を1画面に出すと確実に固まる
2. **水槽を増やす動機が最初から組み込まれる。** §12 の展開が
   「あとから足した機能」ではなく、最初から必要なものになる
3. **どれを入れるか選ぶ楽しみが生まれる。** 全部入れられないので、
   淡水だけの水槽、深海だけの水槽、といったテーマ分けが自然に発生する

初期は1水槽。増設は §12 のとおりポイントで行う。

### 11.2.6 324体をどう描くか — 型 × 色

**1体ずつ描かない。** 25種類の形の型を用意して、色2色とサイズで描き分ける。

| ファイル | 役割 |
|---|---|
| `docs/scripts/fish_shapes.py` | 名前から形の型と色を判定して `creatures.json` を作る |
| `docs/data/creatures.json` | 324体ぶんのパラメータ（名前・★・型・色2色・動き） |

型の判定は名前から自動でやる。「〜ガニ」なら crab、「〜イカ」なら squid。
色も名前から拾う（アカ→赤、クロ→黒、コガネ→金）。
**日本の魚の名前は見た目がそのまま名前になっているものが多いので、これがよく当たる。**

当たらないものは `EXCEPT` と `OVERRIDE` に1行書いて上書きする。

**型の内訳（25種類）**

```
fish 127  weed 23  crab 17  shrimp 17  eel 14  spiral 14  shell 11
jelly 11  squid 11  shark 11  flat 9  worm 8  puffer 7  octopus 7
deep 6  whale 6  seahorse 5  star 4  urchin 3  cucumber 3  coral 3
barnacle 2  turtle 2  ray 2  angler 1
```

> **自動判定でやらかしたこと（記録）**
>
> | 誤り | 原因 |
> |---|---|
> | オイカワがイカになった | 「イカ」の部分一致。淡水魚 |
> | ムラサメモンガラがサメになった | 「サメ」の部分一致 |
> | アカニシがカニになった | 「カニ」の部分一致 |
> | マガレイがカレイと判定されなかった | 濁音「ガレイ」を書き忘れ |
> | **キビナゴ・マカジキ・スズキ・イサキなど25体が黄色になった** | **色語に「キ」を入れていた** |
> | アオサ・アオノリが青くなった | 「アオ」を青と判定。海藻は緑 |
>
> 部分一致は必ず誤爆する。**色語は先頭一致のみ・2文字以上**に限定し、
> 海藻は名前を無視して緑にする、という形で決着した。
> 新しい名前を足したら、必ず `fish_shapes.py` を実行して結果を目で見ること。

### 11.3 描画の制約（§5.4 の再掲）

- **SVG ＋ CSS アニメーションのみ。** canvas / WebGL は使わない。
  `requestAnimationFrame` を回すとモバイルのバッテリーを食い、
  タブを開きっぱなしにされたときにCPUを占有する。
  CSSアニメーションならブラウザが裏タブで自動的に止める
- **同時に動かすのは種類ごとに1〜3体まで。** 同種が32匹いても
  泳がせるのは数体で、残りは「×32」と数字で出す。
  500匹をDOMに出すと固まる
- **絵は1体1ファイルにしない。** SVGのパスを文字列としてまとめ、
  色とサイズをデータで持つ。300体ぶんのファイルを管理しない

### 11.4 試作で分かったこと

30体を実際に描いて動かしたところ、以下が確認できた。

- 4種類の動きで、水槽として成立する
- タチウオ（縦長）やチンアナゴ（砂から生える）のように、
  **型に収まらないものが少数ある。** 例外は「固定」型に寄せれば吸収できる
- 深海の生き物（チョウチンアンコウ・シーラカンス）は下の層に置くと映える。
  **★が高いほど深い位置に配置する**と、水槽を見ただけで実力が伝わる

## 12. 今後の展望 — ポイントの使い道を増やす

**魚が増えるだけだと、いずれ頭打ちになる。**
「勝ってもポイントが余る」状態に戻ると、また出口の問題が再燃する。

そこで、水槽そのものを育てる方向に広げる。

| 段階 | 内容 | ポイントの役割 |
|---|---|---|
| 第1段階（いま設計中） | 的中すると生き物が増える | 使わない。的中が通貨 |
| 第2段階 | **水槽を増やす**（淡水槽・海水槽・深海槽など） | 増設にポイントを使う |
| 第3段階 | **インテリアを置く**（岩・流木・沈没船・水草・照明） | 購入にポイントを使う |
| 第4段階 | **レイアウトを組む**（配置・背景・水の色） | 見せ合いの対象になる |

**ここで初めてポイントに使い道ができる。**
ただし §9 の禁止事項は変わらない。

- インテリアは **ポイントで買えるが、売れない・譲れない・戻せない**
- **ガチャにしない。** 「ポイントを払って偶然で中身が決まる」構図は作らない。
  一覧から選んで買う形にする

生き物が「実績の記録」、インテリアが「ポイントの出口」と役割を分ければ、
どちらの性質も濁らない。**この分離は最初から守っておくこと。**

  レスポンスサイズもCPU時間も測れば分かる。**公開前に §5.5 の手順で必ず測る。**
- **Supabase Nano の実効スループット** は公式に明示されていない。
  「同時100人前後」は共有CPUインスタンスの一般的な感触であって、根拠のある数字ではない。
- **場のご当地魚24種**（§2.2）はご当地性の強さで選んだだけで、裏取りしていない。
- **法的な判断は弁護士のものではない。** §4.1 は刑法185条の条文と実装を
  突き合わせただけの整理で、これをもって適法性が保証されるわけではない。
  公開規模が大きくなるなら、一度専門家に見てもらったほうがいい。
